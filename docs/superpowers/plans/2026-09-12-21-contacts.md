# Track H (v1.2) — Contacts (evolve Payee → Contact) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Evolve the one-directional Payee into a first-class **Contact** — a party (person **or** company), already usable on any transaction (income or expense, since the field is direction-agnostic), now with an **avatar** and a click-through **overview** (money in / out / net, by-category, recent transactions). Full rename `payee → contact`, `payee_id → contact_id` app-wide (pre-1.0, demo-only — clean, exactly like we replaced free-text payee with the entity).

**Architecture:** Migration 0014 renames the `payees` table → `contacts` and `payee_id` → `contact_id` (on `transactions` AND `scheduled_transactions`), and adds `contacts.type` (person|company) + `contacts.avatar` (a size-capped base64 data-URI, nullable). The image is a **base64 data-URI column** (downscaled client-side, capped ~64KB) — no separate image service/endpoint; a reusable `ImageUpload`/`Avatar` web component handles capture + fallback and will be reused by Subscriptions. Everything else (default category, spending breakdown) carries over, renamed.

## Global Constraints
- Follow `docs/CONVENTIONS.md` (layering; services flush/routers commit; §6 keyset; §7 events/allowlists; §8 parity; §9 tokens). Money integer minor units. Conventional commits, **no trailers**. Baseline at branch start: backend 562 pytest, web 736 vitest.
- **Do NOT edit historical migrations** (0007 defined `payees`, 0011 the scheduled `payee_id`) — 0014 renames the live schema forward; the older migrations stay as they were.
- `avatar` is bulky image data → **exclude it from the audit allowlist** (record other contact fields; avatar changes aren't audited — non-sensitive, just bulky). Cap the data-URI size server-side (~64KB) and validate it's `data:image/(png|jpeg|webp);base64,…`.
