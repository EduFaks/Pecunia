# Plan (v1.1 domain) — Planned / Recurring Transactions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** A **Planned** domain (MoneyMatter parity) — recurring/scheduled money you know is coming: salary, rent, subscriptions. A schedule is a *rule* (account, amount, category/payee, frequency, next due date); the user sees what's upcoming and, when it happens, **posts** it (creates the real transaction and advances the schedule) or **skips** it. No auto-posting and no external sync — consistent with Pecunia's manual philosophy; posting is an explicit one-click action.

**Architecture:** New domain mirroring the finance pattern. A `ScheduledTransaction` entity (the recurring rule) + a `ScheduledTransactionService` that computes the next due date via a pure recurrence helper (extends `pecunia/period.py`) and, on `post`, creates a real `Transaction` from the template then advances `next_due`. Feature dir `web/src/features/planned/`, nav label **"Planned"**, route `/planned`. One migration `0011`.

**Tech Stack:** no new deps.

## Global Constraints
- Follow `docs/CONVENTIONS.md` (layering; services flush/routers commit; §3 StrEnum+CHECK; §4 money integer minor units; §6 keyset pagination; §7 events/allowlists; §8 testing/parity; §9 frontend tokens; clock-free services — pass `today`/dates in). Workspace-scoped (D7) + `is_demo`.
- Reuse the existing frequency vocabulary (`weekly|monthly|quarterly|yearly`) as the recurrence frequency; recurrence advance math is pure + unit-tested (clock-free).
- Posting a schedule creates an ordinary `Transaction` (which flows through the normal balance/analytics logic); the schedule row is never itself a transaction. Conventional commits, **no trailers**. Baseline at branch start: backend 443 pytest, web 664 vitest green.

**Interfaces:**
- `ScheduleFrequency(StrEnum)`: `WEEKLY/MONTHLY/QUARTERLY/YEARLY`.
- `ScheduledTransaction`: `id` uuid PK; `workspace_id` FK→workspaces CASCADE NOT NULL idx; `account_id` FK→accounts CASCADE NOT NULL; `category_id` FK→categories SET NULL; `payee_id` FK→payees SET NULL; `amount_minor` BigInteger NOT NULL (signed — negative = expense, positive = income, same convention as transactions); `currency` String(3) NOT NULL; `description` Text NOT NULL; `frequency` Text NOT NULL CHECK in the enum; `interval_count` Integer NOT NULL server_default `1` (every N periods); `next_due` Date NOT NULL; `end_date` Date NULL; `is_active` Boolean NOT NULL server_default true; `is_demo` bool; timestamps.
- `period.advance(d: date, frequency: str, interval: int = 1) -> date`: weekly → +7*interval days; monthly/quarterly/yearly → add 1/3/12 * interval months (clamp end-of-month like the existing month math). Pure, clock-free.

### Task 2: ScheduledTransactionService + endpoints (CRUD, post, skip)

**Files:** Create `api/src/pecunia/services/scheduled_transactions.py`, `api/src/pecunia/api/scheduled_transactions.py`; modify `api/src/pecunia/main.py`, `api/src/pecunia/audit/actions.py` + `activity/templates.py`; tests `api/tests/test_scheduled_transactions.py`.

**Interfaces:**
- `ScheduledTransactionService(db)` (flush, never commit): `create` (validate account/category/payee belong to the workspace — 404/422 as the existing patterns do; require `amount_minor != 0`; `next_due` required); `list` (keyset by `next_due` asc — soonest first — with `id` tiebreak; optional `is_active` filter); `get`; `update`; `set_active(sched, bool)` (pause/resume) and/or `archive`; `post(sched, *, on_date=None, today)` → create a real `Transaction` from the template (`account_id, amount_minor, currency, description, category_id, payee_id, occurred_on = on_date or sched.next_due`), advance `sched.next_due = period.advance(next_due, frequency, interval_count)`, and if `end_date` is set and the new `next_due > end_date` set `is_active=False`; emit `scheduled_transaction.posted` (+ the created `transaction.created` event flows normally); return (schedule, created transaction); `skip(sched)` → advance `next_due` without creating a transaction (same end-date deactivation), emit `scheduled_transaction.skipped`.
- Endpoints `/api/v1/planned` (require_workspace, require_initialized): POST 201, GET list, GET/{id}, PATCH/{id}, POST/{id}/post (→ 201 with the created transaction + updated schedule), POST/{id}/skip, DELETE/{id} (or archive). `ScheduledTransactionOut` = the allowlist fields + timestamps.

## Self-review notes
- **Coverage:** schedule entity + pure recurrence advance (T1), CRUD + post (creates real tx + advances) + skip + pause + end-date deactivation (T2), full UI incl. list, form, post/skip/pause, nav (T3). Posting flows through the ordinary transaction path so balances/analytics/audit all update for free.
- **Consistency:** mirrors the finance domains layer-for-layer; reuses `period.py` (advance alongside current_window), the pickers, `MoneyText`/`MoneyInput`; StrEnum+CHECK for frequency; allowlist has no secret-like fields; keyset pagination.
- **Manual philosophy:** no auto-posting, no external calendar/bank sync — posting is an explicit user action; a schedule is a convenience/reminder, not an automation.
- **Deferred:** auto-post option and richer recurrence (nth-weekday, semi-monthly) — out of V1.1 scope; a future enhancement.
